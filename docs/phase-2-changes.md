# Phase 2: typed outputs, exceptions and decision proofs

Phase 2 of the [redesign](2026-10-30-refonte-run-iq-design.md) makes Run-IQ a generic decision engine: a rule contributes to a typed output, rules can carry exceptions, and each decision can be sealed in a proof that a third party verifies without running anything. `@run-iq/spec` defines the formats; `@run-iq/core` implements them. This page lists what changed in `@run-iq/spec`, task by task, as the code stands; where a later task changed an earlier rule, the earlier section says so.

## Versions

| Package        | Before         | Now            |
| -------------- | -------------- | -------------- |
| `@run-iq/spec` | `1.0.0-next.0` | `1.0.0-next.1` |

Dependants that use `^1.0.0-next.0` accept the new version. Node.js 20.19 or later is required, the floor of `@noble/hashes` and `@noble/curves`.

## Formats

`@run-iq/spec` defines one frozen proof format and three annex formats, four document formats in all, and one domain tag, that of the input tree, which names no document. Each document names its format in a `format` member, and every reader checks it first.

| Format                 | Constant             | Document                                    | Since    |
| ---------------------- | -------------------- | ------------------------------------------- | -------- |
| `run-iq.proof/1`       | `PROOF_FORMAT`       | `DecisionProof`, a sealed decision          | Task 9   |
| `run-iq.input/1`       | `INPUT_TREE_TAG`     | a domain tag, not a document (D-15)         | Task 9H1 |
| `run-iq.referential/1` | `REFERENTIAL_FORMAT` | `Referential`, a dated code system          | Task 9E  |
| `run-iq.disclosure/1`  | `DISCLOSURE_FORMAT`  | `FactDisclosure`, facts shown from an input | Task 9H2 |
| `run-iq.attestation/1` | `ATTESTATION_FORMAT` | `Attestation`, a detached signed statement  | Task 9K2 |

- **`PROOF_FORMATS` lists the proof formats accepted forever** (D-6), frozen; it holds `run-iq.proof/1` alone. A new value of a closed enumeration, or a new required field, makes a following format; it is added to the list and the earlier one stays verifiable. A format outside the list gives the single issue `unknown format: <format>` (cited, at most 256 code units), with no other issue, in `validateProof`, `verifyProof`, `sealProof` and `signProof` (`INVALID_PROOF`); the same holds for a disclosure (`verifyFactDisclosure`) and an attestation (`verifyAttestation`).
- **The domain tag of a proof is its format** (D-16): every leaf and the digest start with `T = utf8(format) ‖ 0x00`, so a following format changes every leaf and every digest, and a proof cannot be read as one of another format.
- **What stays open** (D-6): the reasons of an exclusion and of a pending rule are open strings (a reason this version does not know is accepted and means nothing more), and so is the `kind` of an attestation. The causes of a pending `ERROR` are closed (`ERROR_CAUSES`, Task 9J): a new cause is a new format.
- Each document format has a JSON schema (draft 2020-12) exported by the package (the input tree tag has none: the input itself is described by `schema/proof-input.schema.json`): `schema/decision-proof.schema.json`, `schema/proof-input.schema.json`, `schema/referential.schema.json`, `schema/fact-disclosure.schema.json`, `schema/attestation.schema.json`, beside `schema/rule-definition.schema.json` and `schema/output-declaration.schema.json`. Each accepts what its validator accepts on JSON documents; what JSON Schema cannot express (lone surrogates, the value budget, digests and signatures, orders) is listed in its description and checked by the validator alone.

## Before Task 9C: outputs, exceptions and the first proofs

### Output declarations

- `OutputDeclaration` is `{ type, combine, values? }`. The types are `number`, `boolean`, `string`, `enum`, `list` and `object`; the strategies are `sum`, `max`, `min` (numbers), `all`, `any` (booleans), `union` (lists) and `highestPriority` (any type).
- `values` is required for an `enum` (distinct non-empty strings, at least one) and refused for any other type.
- `validateOutputDeclaration(d)` returns every problem with its path and never throws. `valueMatchesOutputType(value, d)` checks a value against a declaration.
- `DEFAULT_OUTPUT` is `value`, the output of a rule that names none. `DEFAULT_OUTPUT_DECLARATION` is `{ type: 'number', combine: 'sum' }`, frozen.
- `schema/output-declaration.schema.json` (exported as `@run-iq/spec/schema/output-declaration.schema.json`, Task 9I) describes a declaration; it agrees with `validateOutputDeclaration` (see below).

### Decimals, rounding and strata

- **`OutputType` gains `decimal`.** A decimal output holds an exact decimal as a canonical string: no exponent, no leading zero, no trailing fractional zero, no `-0` (`"1234.5"`). `sum`, `max`, `min` and `highestPriority` combine it; `union`, `all` and `any` do not. `valueMatchesOutputType` accepts only a canonical string, never a number. `number` stays a floating-point value: an amount is declared `decimal`. A `switch` over `OutputType` needs the new case.
- `isCanonicalDecimal(text)` tells a canonical decimal. `toCanonicalDecimal(text)` writes `-?digits(.digits)?` canonically (`"0012.50"` gives `"12.5"`, `"-0.0"` gives `"0"`), for any number of digits, and is idempotent. It refuses anything else, an exponent, `+`, spaces, `".5"` or `"5."`, with the new error code **`INVALID_DECIMAL`**. Both are pure text functions, with no dependency, in both entries.
- `OutputDeclaration` gains `rounding?: { scale, mode, at? }`, for `number` and `decimal` outputs only: `scale` an integer from 0 to 20, `mode` one of `halfUp`, `halfDown`, `halfEven`, `up`, `down`, `ceiling`, `floor` (`RoundingMode`), and `at` `output` (the default) or `contribution`. `validateOutputDeclaration` checks it.
- `OUTPUTS_VARIABLE` is `$outputs`, the reserved variable through which a rule reads an output (`$outputs.x`).
- **Output names starting with `$` are reserved.** `validateRuleDefinition`, `normalizeRuleDefinition` (`INVALID_RULE`) and the rule JSON schema refuse them in `output`, in a `shortCircuit` `output` and in selector `outputs`: `<path> must not start with "$": output names starting with "$" are reserved`. A rule that used such a name must be renamed.
- **The proof gains required fields.** `UnsignedProof.strata` (`string[][]`) lists the outputs of each evaluation stratum, in order; a stratum may be empty, and a rule set where no rule reads an output has one stratum. `ProofStep`, `ProofSkip` and `ProofException` gain a required `stratum`, a safe integer index in `strata`. `ProofStep` gains `unrounded?`, the contribution before rounding, and `ProofOutput` gains `rounding?`, checked as in a declaration. The format stays `run-iq.proof/1`: it was not published before this change. **A proof sealed before this change is refused**: `validateProof` and `verifyProof` report `strata is required` (and `applied[0].stratum is required` and so on for each trace entry), and `sealProof` and `signProof` throw `INVALID_PROOF`. Seal it again from its decision.
- `verifyProof` makes a proof `invalid`, and `sealProof` and `signProof` refuse it (`INVALID_PROOF`), when `strata` contradicts the rest of the proof: `stratum output unknown: name`, `stratum output repeated: name`, `output not in strata: name`, `stratum out of range: id@version`, `step stratum mismatch: id@version`; when an output name starts with `$` (since Task 9J, a shape error of `validateProof` at `outputs[i].name`); and when a `decimal` output's value, or the `contribution` or `unrounded` value of an applied rule for it, is not a canonical decimal string (`decimal value not canonical: name`). These are consistency checks: `validateProof` and the JSON schema check only the shape of the new fields, and agree on it.

### Exceptions

- **`exceptions` is now a closed format**, where phase 1 accepted any JSON value. Each item is `{ kind: 'inhibit', targets }`, `{ kind: 'substitute', targets, params }` or `{ kind: 'shortCircuit', output, value, reason? }`, and nothing else. A rule whose `exceptions` does not follow it is refused by `validateRuleDefinition` and the JSON schema, and `normalizeRuleDefinition` throws `INVALID_RULE`, so it has no checksum.
- `targets` is a `RuleSelector`: `{ ids?, tags?, dimensions?, outputs?, models?, ruleSets? }` (`ruleSets` since Task 9F). Fields combine by AND, the values of one field by OR, and a selector must constrain at least one field. `matchesSelector(rule, selector, carrier?)` implements it, with the name resolution of Task 9F; `outputs` compares the rule's output, `value` (`<pack>:value` for a rule of a pack) when it names none.
- **`exceptions: []` is the same rule as an absent `exceptions`**, with the same checksum and fingerprint (`null` too). In phase 1, `[]` sealed differently: a rule sealed with `exceptions: []` must be sealed again.
- Normalization sorts and deduplicates `ids`, `tags`, `outputs` and `models` in each selector and drops empty fields, so their order does not change the checksum. The order of the exceptions is kept and does.
- `EXCEPTION_MODEL` (`@run-iq/exception`) is a reserved model: such a rule computes nothing, has a non-empty `exceptions` list and no `output`.

### Decision proofs

- `PROOF_FORMAT` is `run-iq.proof/1`. `UnsignedProof` holds the request id, the evaluation and sealing dates, the input digest, the rules received (`{ id, version, checksum, sourceRef? }`), an optional pack reference (replaced by `ruleSets` in Task 9J), the engine, plugin and DSL versions, the outputs, the rules applied and skipped, and the exceptions that took effect. **It holds the digest of the input, never the input.**
- `sealProof` returns a detached copy with `digest` (since Task 9K1, `sealProof(content, seed?)` salts the entries and the digest is that of the proof tree; before it, the sha256 of the canonical proof without `digest` and `signature`). It refuses (`INVALID_PROOF`) an invalid proof, and a proof that cites a rule its `rules` does not list: in `applied`, `skipped`, `pending` or `exceptions` (by qualified id and version), or in output `contributors` or exception `affected` (by qualified id). It does not sort lists: since Task 9J every list must already be in its one order, and an unsorted one is refused, so the same decision always gives the same digest.
- `signProof(p, privateKey, keyId)` signs the 64 characters of `digest` with ed25519 and stores `{ alg: 'ed25519', keyId, value }`, `value` in base64url without padding. It refuses a proof whose digest does not match its content or that cites an unlisted rule (`INVALID_PROOF`) and a malformed key (`INVALID_KEY`). `createSigningKeyPair()` returns hex keys.
- `verifyProof(p, { trustedKeys?, rules? })` never runs anything and never throws. It returns `authentic` (digest matches, signed by a trusted key), `consistent` (digest matches, but unsigned or signed by a key that is not trusted), their redacted forms `authentic-redacted` and `consistent-redacted` (a proof with a redacted entry, since Task 9K1: see "The proof tree and redaction") or `invalid`, with short issues such as `digest mismatch`, `unsigned`, `untrusted key`, `signature invalid`, `cited rule not listed: id@version` (or `: id`), `rule missing: id@version`, `unexpected rule: id@version` and `rule checksum mismatch: id@version`. **An unsigned proof is never `authentic`.** The proof is read once into a JSON snapshot and every check runs on it; act on verified data (a JSON copy), not on a live object.
- `validateProof(value)` checks the shape and returns `{ errors, issues }` like `validateRuleDefinition`. It never throws: a value that cannot be read (a throwing getter or Proxy trap) gives `proof could not be read: <reason>`, and `sealProof` and `signProof` throw `INVALID_PROOF` for it. An unknown key is refused, in a proof as in an output declaration and its `rounding`; a key whose value is `undefined` counts as absent, known or not. The proof is read once: `sealProof`, `signProof` and `verifyProof` check and hash a snapshot built from the very values validated. The JSON schema `schema/decision-proof.schema.json` accepts the same proofs, except that it cannot refuse a rule listed twice.
- **`SpecErrorCode` gains `INVALID_PROOF`, `INVALID_KEY` and `INVALID_DECIMAL`.** A `switch` that covers every code needs the three new cases.

### Portable hashing

- `sha256Hex(text)` is a pure JavaScript sha256 (`@noble/hashes`). spec no longer imports `node:crypto`. Checksum values do not change.
- Both entries export `sha256Hex` and the whole proof API. `@run-iq/spec/canonical` still imports no Node.js module: `sha256Hex(canonicalRulePayload(rule))` gives the checksum, and `verifyProof` runs in a browser.

## Pointers, subjects, reserved names and formats (Task 9C)

- **One path grammar, RFC 6901 (D-1).** `JsonPointer`, `parsePointer` (decoded segments; `~` must be followed by `0` or `1`), `formatPointer` (its inverse) and `comparePointers` (decoded segments compared one by one in UTF-16 code units, a pointer before its descendants: `/a` < `/a/b` < `/a-c`; comparing the escaped text would put `~` after `/`). A list index is written `0|[1-9][0-9]*`: `/x/01` is a valid pointer that names no element. Reads (`listVariables`, facts read, missing facts, assertion keys, `missing`) are pointers into the evaluation context (`/revenue/total`, `/$outputs/risk`, `/$dates/effective`); leaves of the input tree are pointers into the input (`/data/…`, `/meta/…`). `contextToInputPointer` links them: `/x/y` is `/data/x/y`, `/$dates/n` is `/meta/dates/n`, `/$dimensions/k` is `/meta/dimensions/k`, any other engine variable and the root give `undefined`, and a `-` segment is refused in a read (`'-' is not an index`). Segments are compared as written, without Unicode normalization. Errors throw `SpecError` `INVALID_PATH`.
- **Subjects (D-2).** A `Subject` is a pointer naming the collection element an instance is about, by key, never by index: `/households/@h1/people/@a7`. `elementSegment(key)` writes `@<key>` (a string, or a safe integer in decimal: `7` and `'7'` are one key), `groupSegment(value)` writes `!group=<value>` under the same rule; `!segment=<from>..<until>` (two real civil dates, `from` before `until`) is the other reserved segment. `isSubject` checks the syntax and never throws; `subjectContains(scope, subject)` is a prefix test by segments (a subject contains itself; `/a/@f1` does not contain `/a/@f10`) and throws `INVALID_PATH` for a non-subject. A rule without `forEach` has no subject.
- **Reserved names (D-3).** `ENGINE_VARIABLES` lists the fourteen engine variables (`$outputs`, `$dates`, `$dimensions`, `$item`, `$index`, `$params`, `$selected`, `$bounds`, `$parent`, `$prev`, `$children`, `$segment`, `$group`, `$ref`), frozen; `isReservedName` is true for any name starting with `$`.
- **Numbers and texts (D-5).** `canonicalize` is JCS (RFC 8785), tested on the vectors of the RFC. A string or key holding a lone UTF-16 surrogate has no canonical form: `canonicalize`, and so every checksum and digest, throws `NON_SERIALIZABLE` for it (a key is reported at its object's path). `parsePointer` and `formatPointer` refuse one too.
- **Proof formats (D-6).** `PROOF_FORMATS` and the single `unknown format: <format>` issue (see "Formats"). A `format` that is not a string gives `format must be one of run-iq.proof/1`.
- **New error codes.** `INVALID_PATH`, `INVALID_INPUT`, `INVALID_REFERENTIAL`, `INVALID_DISCLOSURE` and `INVALID_ATTESTATION`; `SpecErrorCode` now has eleven codes. A message cites caller text escaped and cut at 256 code units (`CITE_LENGTH`, Task 9G; 100 in Task 9C).
- **Behaviour changes.** A lone surrogate is refused by `canonicalize` (no existing checksum changes: no rule held one). The proof `format` messages changed as above (`format must be "run-iq.proof/1"` before).

## Civil time, time zones and rule versions (Task 9D)

- **Civil dates and instants.** `CivilDate` (`YYYY-MM-DD`) and `Instant` (`YYYY-MM-DDTHH:MM:SS.sssZ`, the canonical form) are text types; `isCivilDate` and `isInstant` check them (never throwing). `toReferenceDate` reads a `Date` or a text: a civil date stays civil; a date-time must have seconds, 0 to 3 decimals and `Z` or `±HH:MM`, in the years 0000 to 9999 before and after its offset; anything else (no seconds, 4 or more decimals, a leap second, an expanded year, non-ASCII digits) is `INVALID_DATE`.
- **Time zones (D-12).** `isTimeZone` accepts `UTC`, `±HH:MM` (HH at most 23) and an IANA name `Area/Location[/…]` by its syntax; `normalizeTimeZone` writes `+00:00` and `-00:00` as `UTC`. Whether an IANA name exists, and where its days start, is the business of a `CivilCalendar` (`civilDateIn`, `startOfDayIn`) the caller supplies: spec embeds no time zone database, and computes UTC and fixed offsets alone.
- **`version` of `tzdata` is the IANA release name** (D-12, D-25). When `@run-iq/core` resolves an IANA name, the proof cites the component `{ name: 'tzdata', version, declaredBy: 'engine' }`, `version` the name of a release of the IANA database (`2026c`), so a verifier in another language pins the same release and a replay reports a change of database. An unknown version is refused by core (`TZDATA_UNKNOWN`, Task 9J). spec checks the component's shape only.
- **Civil bounds stay civil (D-13).** A rule bound written `YYYY-MM-DD` stays a civil date after normalization (it was converted to midnight UTC), so the checksum of such a rule changes (D-36); instants are written canonically. Both bounds have the same form (`effectiveFrom and effectiveUntil must both be civil dates or both instants`; `effectiveUntil: null` goes with both). A rule gains `timeZone?` (normalized) and `effectiveOn?`, the pointer of the date its window is compared with (`/$dates/<name>`, `/$item/…` with `forEach`, `/$segment/…` with `forEach.segments`; default `/$dates/effective`). Both are reserved field names.
- **`windowContains(rule, at, timeZone, calendar)`** compares a window with a reference date in the rule's own time zone (its `timeZone` wins): civil against civil; an instant becomes a civil date in the zone; the calendar is called only when the forms cross. `isEffectiveAt` goes through it in `UTC` with fixed offsets only, and throws `INVALID_DATE` for civil bounds under an IANA zone (`use windowContains with a calendar`).
- **`findOverlappingVersions(rules, timeZone, calendar)` (D-31)** groups the versions by (rule set, `id`) and reports the pairs that cannot coexist: different `effectiveOn` (`kind: 'effectiveOn'`), or windows that can both hold on some reference date (`'overlap'`), each version in its own zone, forms compared in instants when they differ. It returns `{ overlaps, truncated }` (`VersionOverlapReport`, at most 100 pairs, Task 9G) in O(n log n + k), and refuses the same (rule set, `id`, `version`) twice (`duplicate rule R1@1`).
- **Behaviour changes.** Checksums of rules with civil bounds; a date-time without seconds, with 4 to 9 decimals (truncated before) or outside 0000 to 9999 is refused; mixed bound forms are refused; `ExecutableRule.effectiveFrom/Until` are `CivilDate | Date`; the date messages are longer and list the accepted forms.

## Structured dimensions and dated referentials (Task 9E)

- **Dimension specs (D-18).** A rule dimension is a value or `{ ref?, anyOf, except?, match? }` (`DimensionSpec`). A value is non-empty; a qualified value `<system>:<code>` splits at its first `:`, both parts non-empty. The normal form sorts `anyOf` and `except` without duplicates, drops `except: []` and `match: 'any'`, and writes `{ anyOf: [v] }` alone as `'v'`. Selectors compare normalized written forms, never memberships.
- **Referentials (D-35).** `Referential` (`run-iq.referential/1`): codes with dated periods and groups with dated members (`Period`, `ReferentialMember`), each with an optional `sourceRef`. `validateReferential(r, { maxNodes, maxDepth })` never throws and checks size before reading (nodes counted from lengths), periods (not empty, no overlap), codes against groups, cycles and nesting depth at every date by a sweep of the period bounds, and its own work (`referential too complex`). `normalizeReferential` gives the normal form, `computeReferentialDigest` its digest. `schema/referential.schema.json` describes it.
- **Membership.** `resolveMembership` and `matchDimension` answer in three values (Kleene): a group is exhaustive or not; a code invalid at the date, or of another system, is unknown; a referential that declares `codes` makes a value outside them unknown. `via` lists the groups crossed, independent of the order of the members.
- **Behaviour changes.** An empty dimension value is refused; a non-string dimension gives `dimensions.k must be a value or an object { ref?, anyOf, except?, match? }`; `matchesSelector` may throw `INVALID_RULE` for an invalid dimension spec. Checksums of rules with text dimensions do not change.

## Collections, rule sets and selectors (Task 9F)

- **`forEach` (D-2, D-20, D-22).** A rule runs once per element of a collection: `path` (a pointer into `data`, `*` one level per list; not the root, no leading, trailing or doubled `*`, no `-`, no literal segment starting with `@` or `!`, no `$` head), `key` (one name, or one per level), `orderBy` (`{ path, type, dir }`, types `number`, `decimal`, `date`, `dateTime`, `string`; equal on every key is a tie, and the identity key never breaks a tie), `dimensions` (name to pointer in the element), `recurse` or `groupBy` (exclusive), or the `segments` form `{ from, until, facts }` (two different `/$dates/<name>`, sorted fact pointers). `forEach` and `ruleSet` were free extensions before: an old shape is refused.
- **Rule sets and names (D-4, D-37).** `ruleSet` is a pack id or `local` (`LOCAL_RULE_SET`, dropped by normalization). A rule set id matches `^[a-z0-9][a-z0-9_-]*$`: no `.`, since a version is never part of an id and a qualified name must stay readable by every DSL (round 1). `packIdProblem` refuses `local` as a pack. `qualifyName(set, name)` writes `<set>:<name>` (a local name stays bare); a name qualified by the rule's own set is written bare (one meaning, one checksum). A rule `id` holds no `:`; an output name holds no `.` and at most one `:`; `local:` is never written.
- **Selectors.** `RuleSelector` gains `ruleSets`. `matchesSelector(rule, selector, carrier = 'local')` resolves bare names in the carrier's set, a rule's id and output in its own set, and the default output of a pack rule as `<pack>:value`; a selector without `ruleSets` targets the carrier's set only. `ruleSets` alone does not constrain a selector.
- **`findOverlappingVersions`** checks `ruleSet` against the grammar; `local` and absent form one group.
- **Behaviour changes.** The refusals above (`:` in ids, `.` in output names, `local:`, a rule set id outside the grammar); the selector shape message lists `ruleSets?`; `matchesSelector` takes the carrier.

## Decision inputs, and reading untrusted values (Task 9G)

- **`ProofInput` (D-11, D-18).** `{ data, meta: { tenantId, dates, tags, dimensions, context, assertions } }`, every member required. `meta.effectiveDate` is gone: named dates live in `meta.dates` (`effective` is the reference date), each a civil date or a canonical instant. `tags` are sorted without duplicates. A dimension is a value, or a list of at least two sorted values. `validateProofInput(value)` returns every problem with a JSON pointer path (`/meta/assertions/~1revenue/method`) and never throws; `schema/proof-input.schema.json` agrees with it.
- **Refused in an input** (D-3, D-5): a number of absolute value 2^53 or more (it is always an integer in IEEE 754), a root key of `data` starting with `$` (`reserved key /data/$x`), a `$` dimension name, an empty tag or name, an offset date, a lone surrogate, and anything that is not JSON (`<pointer> is not JSON: …`).
- **Assertions.** `meta.assertions` maps a fact pointer (or `/$dates/<name>`, `/$dimensions/<name>`, `''` for everything) to a `FactAssertion` `{ by, method, at, status, basis?, evidenceDigest?, confidence?, complete?, source? }` (nine methods, three statuses `proposed`, `validated`, `contested`; `confidence` in [0, 1]; `complete` only `false`, its one written form; `source` `{ proofDigest, output, subject? }` with `method: 'decision'` only). `governingAssertion` finds the one with the longest prefix by segments, `isProvisionalAssertion` is true for the statuses `proposed` and `contested` and for the method `presumed`, and `computeAssertionDigest` hashes one.
- **Temporal facts.** `validateTemporalFact(value, path)` checks a list of periods `{ from, until, value }` (`until` written, `null` for no end; sorted by `from`; no overlap), with pointer paths.
- **Reading untrusted values: one baseline for every function of the package** (rounds 3 to 13). Every reader goes through `src/input/read.ts`: each property read once into a plain copy, every later check on that copy, so a getter or a Proxy cannot show two values. A value that cannot be read gives a named problem, never a raw error. Problems are listed at most 100 (`further problems not listed (limit 100)`), paths and messages cut at 1,024 code units, caller text cited escaped and cut at 256 (`citeName`). Only the package's own `SpecError` is trusted: one built by the caller and thrown from a getter is cited like any other value.
- **Unreadable input never escapes as a raw error.** A getter or Proxy trap that throws gives an issue instead: `validateOutputDeclaration` reports `<path> could not be read: <reason>`; `validateRuleDefinition` reports `<field> could not be read: <reason>` for a field whose value cannot be converted (`params`, `condition.value`, `exceptions`, an extension), and `rule definition could not be read: <reason>` otherwise; `normalizeRuleDefinition` (and every function built on it) throws `INVALID_RULE` with the same message. Every free-form JSON value the format carries (rule `params`, `condition.value` and extension values, proof output values, contributions and unrounded values, and decision input values) nests at most `MAX_JSON_DEPTH` = 1000 levels of non-empty arrays or objects (`{ "a": 1 }` is 1 level), so any consumer of the format (another runtime, a plain `JSON.parse`, a recursive reader) can read every valid document on an ordinary stack. A deeper value is refused with one wording, in rules, proofs and inputs alike: `<path> is nested deeper than 1000 levels`, where `<path>` is its first container past the limit (level 1001; `params.a.a…`, `/data/a/a…`): `NON_SERIALIZABLE` from `normalizeRuleDefinition`, an issue from `validateRuleDefinition`, `validateProof`, `verifyProof`, `validateProofInput` and `validateTemporalFact`. JSON Schema cannot express this limit: only the validators check it, and each schema's description says so. The check walks with an explicit stack and never overflows the call stack. `canonicalize` itself has no limit of depth: it is a pure function, and a value 100,000 levels deep (or more) gives its canonical form. One call reads at most `MAX_JSON_VALUES` = 10,000,000 values of its caller (shared by every walk it makes: `canonicalize`, the copies of free-form values, the readers of rules, proofs, pointers, selectors, output declarations and inputs; a referential's `maxNodes` is capped at the same number): each list's claimed `length` (each object's number of keys) is counted before any element is read, so a sparse array of length 2^32 − 1 or a Proxy claiming 10^12 elements is refused at once with `<path> is too large: more than 10000000 values`. A value is the member of an object or the element of an array, as the JSON text holds it: an object shared by several paths is read once but counted on each path. **A value is counted once**: only reading the caller's value spends; the package's own copies (the snapshot of a proof, a normalized rule, the copy of an input) are hashed without spending again. So every function agrees on the boundary: `validateRuleDefinition`, `normalizeRuleDefinition`, `computeRuleChecksum`, `computeRuleFingerprint` and `canonicalRulePayload` accept a rule of 10,000,000 values and refuse one of 10,000,001; `validateProof`, `sealProof` and `verifyProof` likewise for a proof; `validateProofInput` and `computeInputDigest` for an input. `sealProof` counts the `digest` it adds and `signProof` the `signature` (four values), so whatever they return, `verifyProof` accepts. The rules given to `verifyProof` count in the same call. **Behaviour change:** an input whose JSON text holds more than 10,000,000 values is refused by `validateProofInput` even when shared objects make it small in memory (it accepted one before, but its digest could not be computed). A hole is not JSON: an array with one is refused everywhere, input and format alike, with `<path> has a hole at index <i>: arrays must be dense` (`canonicalize` no longer writes a hole as `null`).
- **`undefined`: one rule everywhere (behaviour change).** A member of an object the format defines whose value is `undefined` is absent, known or not: it is the TypeScript idiom of an optional field, in a rule, a proof, an input, a referential, an assertion or an output declaration alike (an unknown key whose value is `undefined` is no longer refused, and a required one is missing). Inside a free-form JSON value (rule `params`, `condition.value`, extension values, a `substitute`'s `params` and a `shortCircuit`'s `value`; proof output values, contributions and `unrounded`; input `data` and `meta.context`; the value of a temporal period) and as an array item anywhere, `undefined` is refused: `<path> is not JSON: undefined`. Before, a rule's free-form values dropped an `undefined` member, which a rule sealed so must be sealed again without it. `canonicalize`, which knows no schema, still leaves out an `undefined` member, but refuses an `undefined` array item (`NON_SERIALIZABLE`, `<path> is not JSON: undefined`) instead of writing `null`. Every digest refuses exactly what its validator refuses: `computeInputDigest` now checks its input as `validateProofInput` does and throws `INVALID_INPUT` (`invalid input: <first problem>`, with its path) where it threw `NON_SERIALIZABLE`; it also refuses what it hashed before though the validator refused it (a `Date`, a number beyond 2^53, a reserved key, a missing field). `governingAssertion` lists the assertion keys once and compares each with the pointer's text: its cost follows the assertions, never the number of segments of the pointer. A `SpecError` built by the caller (thrown from a getter, a Proxy trap or a calendar) is never passed on: it is cited like any other thrown value. `canonicalize` reports a value it cannot read at that value's own path (`r.a.b`), and `sha256Hex` refuses a value that is not a string or a string with a lone surrogate (`NON_SERIALIZABLE`).
- **Other behaviour changes.** The input shape (and so its digest); rules with an empty tag, an empty dimension name or a `$` date name are refused; `findOverlappingVersions` returns `{ overlaps, truncated }` where it returned a list.

## The input tree, the seed and the salted input digest (Task 9H1)

- **Exact encoding of D-15.** One leaf per scalar (`null` included), per list (empty or not; a non-empty list's elements have their own leaves too) and per empty object of the input, at its pointer into `ProofInput` (`/data/…`, `/meta/…`); a non-empty object has no leaf of its own. Leaves are sorted by `comparePointers`, so the descendants of a pointer follow it without interruption. With `T = utf8('run-iq.input/1') ‖ 0x00` (`INPUT_TREE_TAG`):
  - content commitment `C = sha256(0x03 ‖ T ‖ valueSalt ‖ utf8(canonicalize(c)))`, `c` being `['value', value]`, `['array', length]` or `['object']`;
  - leaf `sha256(0x00 ‖ T ‖ salt ‖ C ‖ utf8(canonicalize(pointer)))`: salt and `C` of fixed length first, the pointer last;
  - `salt = HMAC-SHA256(seed, utf8('input:' + pointer))` and `valueSalt = HMAC-SHA256(seed, utf8('value:' + pointer))`, 32 bytes each, raw in the hash, hex in an `InputLeaf`;
  - node `sha256(0x01 ‖ left ‖ right)`, split at the largest power of two strictly below n (RFC 6962), the empty tree `sha256('')`, one leaf its own root;
  - `inputDigest = sha256(0x02 ‖ T ‖ uint64be(n) ‖ root)`: the digest commits to the number of leaves, which a root alone does not (leaf 4 of 7 does not verify as leaf 4 of 8).
- **Seed (D-14).** `deriveInputSeed(secret, requestId)` is `HKDF-SHA256(ikm secret, salt utf8('run-iq.input-seed/1'), info utf8(requestId), 32 bytes)`, the secret 32 bytes or more and the request id non-empty, else `INVALID_KEY`. `UNSALTED_SEED` is 32 zero bytes: the salts are then still HMACs, but public. The seed and the secret never appear in a proof, a disclosure or a message.
- **Frozen vector `tests/vectors/input-v1.json`**, recomputed by an independent Python script (stdlib only: its own HKDF, HMAC, JCS, leaf walk and recursive RFC 6962 root). Secret 32 bytes of `0x42`, request id `r1`, seed `f9b972f50267915261e884526c8553bdf4a353eb2e4e9e78ee65716aeceaacfb`; the input `{ data: { a: 1, b: [], c: {}, d: { e: null } }, meta: { tenantId: 't', dates: {}, tags: [], dimensions: {}, context: {}, assertions: {} } }` has 10 leaves, root `2d91ab26631906a6d21b6019fae601f685822bb54d7711d09bd68041be1fc4cd` and digest `e6085682c2b0c916134bb969f28cc18ac43aa80f90aea10307363ffbb89311ea`; under `UNSALTED_SEED`, digest `75943cba2ddfd689be598415827176947b58369e7bf9a4e1fe94982315b2d9e6`; the empty tree `e3b0c442…b855`. `tests/vectors/input-v2.json` (43 leaves) covers escaped segments, non-ASCII and astral text, index order as text, a non-integer number and nested lists. Both were refrozen in Task 9H2 (rounds 2 and 3) for the commitment `C` and the pointer last.
- **Functions.** `computeInputDigest(input, seed)` (behaviour change: it was `computeInputDigest(input)`, `sha256Hex(canonicalize(input))`) checks the seed first (`INVALID_KEY`), then the input as `validateProofInput` does (`INVALID_INPUT`), and hashes it in one pass. `inputLeaves` and `inputLeafHash` expose the leaves; `verifyInputInclusion(digest, size, index, leafHash, path)` checks one against the digest with its size and never throws; `merkleRoot`, `inclusionPath` and `verifyInclusion` work on the RFC 6962 root itself. `computeIdempotencyDigest({ input, options })` is `sha256Hex(canonicalize(request))`, unsalted, kept by a decision store to recognise a retry and never published (D-17).
- **New refusal:** `validateProofInput`, and so every digest of an input, refuses an input whose leaf pointers hold more than 268,435,456 (2^28) UTF-16 code units in all, each leaf on each path counted (`the leaf pointers of the input hold more than 268435456 code units`): the digest hashes every pointer three times (two salts and the leaf), and a long key above many values, or a value shared by many paths, made that work grow far beyond the size of the input. The time budget of D-26 (an input of 500,000 leaves digested in less than 5 s) is measured by `npm run bench` on the built package, outside `npm test` and CI; the suite bounds the same work by counting it (5 hashes a leaf, the bytes of its pointer and content), never by a clock.
- **No digest builds its text (round 3).** Every digest of spec writes its canonical text into the hash as it is produced, through a UTF-8 encoder (`TextEncoder.encodeInto`) into one fixed 64 KiB buffer, a long string escaped slice by slice: `computeRuleChecksum`, `toExecutableRule`, `computeRuleFingerprint`, `computeReferentialDigest` (and the comparison of referential entries), `computeAssertionDigest`, `computeIdempotencyDigest`, the proof digest (`sealProof`, `signProof`, `verifyProof`), the input leaves and their salts, `sha256Hex` itself, and `fromStoredRecord`'s check that a payload is canonical (compared as written). A valid value whose canonical text is longer than a JavaScript string can be (V8: 2^29 - 24 code units, e.g. several keys sharing a text of 120 million characters, or one text of 2^29 - 34) now has a digest; `canonicalize` of it throws `SpecError` (`NON_SERIALIZABLE`, `Value at "(root)" cannot be serialized to canonical JSON: too long to write as one string`) instead of the engine's `RangeError`. Digest values do not change.
- **`inputLeafHash` refuses every leaf no valid input has (behaviour change).** Besides its shape, a leaf's pointer must name a place where a valid input has a leaf (`/pointer names no leaf of a valid input: <why>`: `/meta` itself, `/meta/<unknown>`, `/data/$x`, an assertion as a whole, anything below a string of `meta`), its kind must be one a leaf there has (`/kind must be object at this pointer`), its value what that place holds (a date, a tag, a dimension value, an assertion field), a list at most `MAX_JSON_VALUES` less the values every input holds and those above it (`/data/a`: 9,999,991; a list of dimension values at least 2), and its pointer at most 2^28 less the shortest pointers of the other parts of an input (268,435,376 below `/data`). A leaf more than `MAX_JSON_DEPTH` (1000) levels below `/data` or `/meta/context` is refused as the validator refuses its container (`/pointer names no leaf of a valid input: it is nested deeper than 1000 levels below /data`), and a list exactly 1000 levels below them holds nothing (`/length must be an integer from 0 to 0`). A leaf is judged alone: its siblings, their order and their share of the budgets are not checked.
- **`merkleRoot` and `inclusionPath` read the leaf hashes straight into one buffer of 32 bytes per leaf** (no array per hash, no copy of the list): 10,000,000 leaves fit in a process of default heap. The elements are read once, in order, and the first problem is the one reported (a bad hash before a hole is reported first).
- **`validateProofInput` keeps no copy of the input**: it counts the leaf pointers as it reads (each object once, its count reused on every path); only the digests make their read-once copy.
- **Two test runs (round 4).** `npm test` runs the fast suite (Vitest project `fast`, files in parallel, no test past about 2 s or 500 MB). `npm run test:heavy` runs `tests/heavy/` (project `heavy`, one file at a time in one worker): the 10M-value boundaries, the 10M-leaf Merkle root, the 2^28 code-unit and 10M-list leaf limits, the 500,000-leaf counters and the digests of texts no string can hold. CI and `ci:local` run it after `npm test` and the build. Every scale test has an explicit timeout, a safety net only: its bounds are proven by counters. `npm run lint` lints `bench/`.

## Fact disclosures and proofs of absence (Task 9H2)

- `discloseFacts(input, seed, present, absent)` returns a `FactDisclosure` (`run-iq.disclosure/1`, `DISCLOSURE_FORMAT`; frozen with `run-iq.proof/1`): `{ format, inputDigest, size, facts, absent }`. `verifyFactDisclosure(d, inputDigest)` checks it against the input digest alone and never throws: `{ valid, issues, facts, lists, absent }`, `facts` the value at each disclosed pointer rebuilt from its leaves, `lists` the length of every list in them, `absent` the pointers proven absent; all three empty when `valid` is false. The JSON schema `schema/fact-disclosure.schema.json` (exported as `@run-iq/spec/schema/fact-disclosure.schema.json`) accepts the same shapes; the cryptographic, order and completeness checks are the verifier's alone. `discloseFacts` lives in `src/input/disclose.ts`, `verifyFactDisclosure` in `src/input/verify-disclosure.ts` (its read-once copy of the disclosure in `src/input/read-disclosure.ts`, the rebuilding of a fact's value in `src/input/rebuild-fact.ts`), the types and rules they share in `src/input/disclosure.ts`.
- **A fact is a whole value.** A present pointer is shown with every leaf at or below it (`DisclosedFact`: `{ pointer, leaves, before?, after? }`), each leaf a `DisclosedLeaf` (an `InputLeaf`, both salts included, with its `index` among the sorted leaves and its RFC 6962 audit `path`, hex, bottom up): a scalar, an empty object or an empty list is its one leaf; a list is its own leaf then its elements; a non-empty object is the leaves of its members. Its leaves sit at consecutive indices, framed by a neighbour before (unless the first leaf is at the pointer, or first in the tree) and a neighbour after (unless the value is a scalar, an empty object or an empty list, or its last leaf is last in the tree), neither inside it. The verifier checks exactly that, and a list lacking an element; a fact with a leaf missing or added is refused (`fact not shown whole: <p> (<why>)`). A present pointer inside another present one is refused (`pointer inside another requested pointer: <p> (inside <q>)`); an absent pointer may be inside a present one.
- **The size is the digest's.** The input digest commits to the leaf count (D-15), and every leaf is checked with `verifyInputInclusion` under the `size` the disclosure states, so a disclosure cannot claim another size: the last leaf of a tree of 10 is not the last of a tree of 11.
- **Proof of absence.** Leaves are sorted by `comparePointers` (decoded segments, a pointer before its descendants, which follow it without interruption). A pointer is absent when two adjacent leaves frame it and the second is not inside it; before the first leaf, that leaf alone (index 0) proves it; after the last leaf, that leaf alone (index `size - 1`). With no neighbour, only the empty tree proves it. Below a scalar, a list or an empty object, both neighbours are given: a neighbour's kind is hidden, so no leaf proves an absence alone by being a scalar.
- **Every conclusion assumes a tree sorted honestly by its signer (D-15).** The digest does not prove that the leaves are sorted; only a replay with the input checks it. The verifier refuses what the shown leaves themselves contradict: leaves out of order, a leaf inside a scalar or an empty object, a list element outside its list, a list lacking an element, an absence a shown leaf or list shows present.
- **What a disclosure reveals.** Each fact in full (pointers, values, both salts of each of its leaves). A neighbour (`NeighbourLeaf`: `{ pointer, salt, commitment, index, path }`) shows only its pointer, its salt and `C`: its kind, its value and its value salt never appear, and its value cannot be changed without changing `C`, so the leaf. **Its pointer is shown:** a proof about one key reveals the keys next to it, so an input whose keys are themselves private should use opaque keys (ids, not names). **The size and the indices are shown:** a disclosure states the input's leaf count (`size`, which the digest commits to) and the index of every shown leaf and neighbour, its rank among the sorted leaves. A rank can tell how many leaves sort before a pointer: the index of the neighbour after an absent pointer, for instance, can reveal the length of a list that sorts before it. Audit paths hold hashes only. The seed and the salts of every other leaf never appear. A disclosure needs a salted input: with `UNSALTED_SEED` (compared by its bytes, so any 32 zero bytes) `discloseFacts` throws `SpecError` `INVALID_DISCLOSURE` (`unsalted input cannot be disclosed`): the salts would be public and a hidden neighbour found by guessing. Erasing the secret cuts the link: under another seed the digest differs and no disclosure verifies against it.
- `discloseFacts` refuses (`INVALID_DISCLOSURE`) a present pointer that names no value (`pointer is absent: <p>`), an absent pointer that is present (`pointer is present: <p>`, also for a non-empty object), a pointer requested twice, a present pointer inside another, and an empty request (`nothing to disclose`). It hashes the tree once, as `computeInputDigest` does: every audit path comes out of the same pass, so its hash work is that of the digest.
- Frozen vectors: `tests/vectors/disclosure-v1.json`, two disclosures of the input vectors (escaped segments, astral text, index order as text, an object, a list of nested lists, an empty list, an absence inside a disclosed object, below a scalar, before the first and after the last leaf), computed by an independent Python script. The input vectors `input-v1.json` and `input-v2.json`, and the disclosure vectors, were refrozen for the leaf encoding with `C` (Task 9H2, round 2), then again when the pointer moved into the leaf hash itself, last, with no hash of its own (round 3).

## Complete output declarations (Task 9I)

- **`OutputType` gains `date` and `dateTime`; `CombineStrategy` gains `count`.** A `date` output holds a civil date (`isCivilDate`: `"2028-02-29"`, never `"2026-02-29"` nor an instant), a `dateTime` output an instant in its canonical form (`isInstant`). `max` and `min` now also combine `enum` (by rank in `values`), `date` and `dateTime` (in time). `count` applies to `number` only: each contribution is a boolean (`contributionMatchesDeclaration`), the value is the count of `true`s, a non-negative safe integer. The admitted combinations: `sum` on `number`, `decimal`; `max`, `min` on `number`, `decimal`, `enum`, `date`, `dateTime`; `count` on `number`; `union` on `list`; `all`, `any` on `boolean`; `highestPriority` on all nine types. A `switch` over `OutputType` or `CombineStrategy` needs the new cases.
- **`rounding.increment`.** A rounding has exactly one of `scale` and `increment` (`OutputRounding.scale` becomes optional): `increment` is a canonical decimal string greater than 0 with at most 20 decimal places (`"0.05"`, `"10"`). Both, or neither, is refused at the rounding's path; `"0"`, `"-1"`, `"0.050"` (`must be written "0.05"`), `"1e-2"` and a number are refused at `rounding.increment`. A rounding on a `count`, a `date` or a `dateTime` is refused. The rounding is specified here and computed by `core`.
- **`unit`, `empty`, `per`, `dimension`, `sign`.** `unit`: a non-empty string without white space around it, on a `number` or `decimal` output. `empty`: a boolean, on an `all` output only; `true` makes an `all` that no rule reached `true`. `sign`: `nonNegative` or `nonPositive`, on a `sum` only; `valueMatchesOutputType` and `contributionMatchesDeclaration` then refuse a value of the other sign. `per`: a pointer to a collection, with the refusals of `forEach.path` (the same code, `readCollectionPath`). `dimension`: a dimension name (not empty, not `-`, not starting with `$`) on a `string` or `enum` output. `per` and `dimension` together: `output: per and dimension are exclusive` (D-19). A text of a declaration (an enum value, `unit`, `per`, `dimension`) with a lone UTF-16 surrogate is refused: it has no canonical form.
- **One written form.** `normalizeOutputDeclaration(d)` returns the normal form: `empty: false`, `rounding.at: 'output'` and `undefined` members are absent, and an increment that is a power of ten from `"1"` to 10^-20 is its `scale` (`"0.01"` is `scale: 2`). Every other member is kept as written; the order of enum `values` ranks them, so it is part of the declaration. `sameDeclaration(a, b)` compares the canonical texts of the normal forms: two declarations that differ by `unit` are not the same (D-9), `empty: false` and an absent `empty` are (pre-flight M-9), and so are their checksums.
- **Statuses.** `OutputStatus` is `determined`, `provisional`, `conflict` or `undetermined`; `OUTPUT_STATUSES` lists them from the weakest to the strongest (frozen), and `joinStatus(a, b)` gives the stronger (D-7). Anything else throws `INVALID_PROOF`.
- **Empty outputs and comparisons.** `emptyOutput(d)` is the output no contribution reached (gap-hunt X-4): `sum` `0` (`"0"` for a decimal), `count` `0`, `union` `[]`, `any` `false`, all `{ value?, status: 'determined' }`; `all` `{ status: 'undetermined' }`, or `{ value: true, status: 'determined' }` with `empty: true`; `max`, `min`, `highestPriority` `{ status: 'determined' }` with no `value` member. `compareOutputValues(a, b, d)` returns -1, 0 or 1: numbers numerically, decimals by exact value (`"10"` after `"9"`), enums by rank, dates and instants in time; it throws `INVALID_RULE` for a type without order and for a value that is not one of the output.
- **Behaviour changes.** Every function that takes a declaration (`valueMatchesOutputType`, `contributionMatchesDeclaration`, `emptyOutput`, `compareOutputValues`, `sameDeclaration`, `normalizeOutputDeclaration`) now checks the whole declaration first and throws `INVALID_RULE` (`invalid output declaration: <first problem>`, the problem's path as `path`) for one `validateOutputDeclaration` refuses: `valueMatchesOutputType` answered for a declaration it only partly read (`{ type: 'string', combine: 'sum' }` gave `true` for a string; an enum without `values` gave `false`; its error messages were worded differently). The members of a declaration are read once each and counted in the value budget (the validator read the top-level members twice and did not count them). An enum value with a lone surrogate is refused. The messages that list the members, the types, the strategies and a rounding's shape (`{ scale or increment, mode, at? }`) list the new ones; `{}` as a rounding now reports `needs scale or increment` at the rounding instead of `scale is required`. The proof format accepts the new types, `count` and `increment` in an output's rounding, in `validateProof` and the JSON schema alike; a proof keeps its rounding as written (the normal form is the business of Task 9J).
- **JSON schema of a declaration (round 2).** `schema/output-declaration.schema.json` accepts exactly what `validateOutputDeclaration` accepts (fuzzed on 20,000 drawn declarations): the combination matrix, `values` on an enum only, rounding (scale XOR increment) and `unit` on a number or decimal only, no rounding on a `count`, `empty` under `all` only, `sign` under `sum` only, `per` with the pattern of `forEach.path`, `dimension` on a string or enum only (not empty, not `-`, not `$…`), `per` and `dimension` exclusive. Only the validator refuses a lone UTF-16 surrogate in a text and spends the 10,000,000-value budget; the schema's description says so.
- **A proof's output agrees with its declaration (round 2, behaviour change).** `validateProof` (and `sealProof`, `verifyProof`) refuse an output whose `combine` cannot combine its `type` (`outputs.<name>.combine "sum" cannot combine a string output: it applies to number, decimal`) and a rounding on a `count`. The proof's `rounding` must be written in its normal form: `at: 'output'` is refused (`… .at must be absent: output is the default`) and so is an increment that is a power of ten (`… .increment "0.01" must be written as scale 2`). The proof schema says the same (the increment pattern excludes `1` and `0.0…1`; `at` is `contribution` only). Before, a proof kept its rounding as written.
- **Values of the declared form (round 2, behaviour change).** `verifyProof` and `sealProof` report, after the non-canonical decimals, by sorted output name: `output value does not match its declaration: <name>` (a value not of its type: a civil date for `date`, a canonical instant for `dateTime`, a non-negative safe integer for `count`, a string for `string` and `enum`, a number for `number`, a boolean, an array, an object; `null` only for a `max`, `min`, `highestPriority` or `all` that no rule reached); `output value not rounded as declared: <name>` (a rounded `number` or `decimal` value off its step, checked exactly: at most `scale` places, or a multiple of `increment`; a `number` rounded at each contribution is not checked on its value, since a binary sum of rounded numbers leaves the step); `contribution does not match its output declaration: <name>` (a contribution or `unrounded` value not of the type, a non-boolean contribution to a `count`); `contribution not rounded as declared: <name>` (`at: 'contribution'`). **Not checked in Task 9I, because a proof did not carry it yet (Task 9J added it to each output of the proof, below):** the enum's `values` (an enum value is only checked to be a string, and its rank cannot be checked), `sign`, `unit`, `empty` (an `all` with no contribution may hold `null` or `true`), `per`, `dimension`, and the output's `status`. Task 9J checks them: the enum value is one of `values`; a `sum` value and its contributions respect `sign`; an `all` with no contribution holds `true` exactly when `empty` is true; a `per` output holds one value per element, in its items.
- **Round 3 (behaviour changes).**
  - An increment has at most 20 digits before its point, as it has at most 20 after it: it lies from 10^-20 to below 10^20 (`… .increment must have at most 20 digits before the point`), in `validateOutputDeclaration`, `validateProof` and both schemas. `scale` is from 0 to 20: the same 20 places. So checking a value against its step works on numbers of at most 55 digits, and `verifyProof` is linear in the digits of the value (a 1,000,000-digit value against the largest increment: one step per 15 digits, counted by a test). Before, a 2 MB proof with a 1,000,000-digit increment took 13.6 s.
  - A `number` output rounds to a `scale` only. An increment on it must be a power of ten from 1 to 10^-20, which is that scale (and is written as it in the normal form); any other increment (`"0.05"`, `"10"`) is refused, by the declaration validator, the proof validator and both schemas: `… .increment "0.05" applies to a decimal output only: a number output rounds to a scale`. A binary number cannot be a multiple of 0.03 in general (1e16 is none), so such a declaration could never be met. Every scale is met by every double: the double nearest a decimal of `scale` places is written back (shortest form) with at most `scale` places (tested on huge, tiny and ordinary doubles, each scale, sealed).
  - With `at: 'contribution'`, only a `number` `sum` leaves its value unchecked against the step (its binary sum leaves it); the value of a `max`, `min` or `highestPriority` is one of its contributions and must be on the step.
  - `valueMatchesOutputType` refuses a `string` value with a lone UTF-16 surrogate, and, on a `string` output that sets a `dimension`, a value that is not a dimension value (`dimensionValueProblem`: `''`, `:TG`, `iso:`). The values of an `enum` that sets a `dimension` must be dimension values (`output.values[1] has an empty code system before ":"`), in the validator and the schema; a value is split at its first `:`, so `a:b:` and `a::` are valid, `:a`, `a:` and `:` are not. Each text pattern of the declaration schema (enum values of a dimension, `unit`, `dimension`, `per`, `increment`) and the increment pattern of the proof schema are checked against their validator on every string of a few characters. `offDeclarationValues` refuses a lone surrogate in a string value too (`validateProof` refuses it first); the dimension check came with Task 9J, which put `dimension` in the proof.

## The full decision proof (Task 9J)

**Behaviour change: the proof format is rewritten.** It stays `run-iq.proof/1`, which was not published; a proof of the earlier shape is refused (`outputs must be a list`, `inputSalted is required`, and so on). Seal it again from its decision. The tree digest of a proof and its redaction came with Task 9K1 (below).

- **Header.** `UnsignedProof` gains `inputSalted` (boolean), `timeZone` (an IANA name, `UTC` or `±HH:MM`, never `±00:00`), `ruleSets` (the rule sets in precedence order: `{ kind: 'pack', id, version, digest, imports?, timeZone? }`, `{ kind: 'local', timeZone? }`, `{ kind: 'referential', id, version, digest }`), `requested?` (the outputs asked for) and `supersedes?` (`{ digest, reason }`). `versions` gains `models` and `components` (`ProofComponent`: `{ name, version, digest?, declaredBy }`, `declaredBy` `engine`, `plugin:<name>` or `model:<name>`). The pack reference `ruleSet` of the header is gone: each rule names its rule set.
- **Ten sections, all lists.** `PROOF_SECTIONS` names them in order: `rules`, `outputs`, `items`, `applied`, `skipped`, `pending`, `exceptions`, `factsRead`, `missingFacts`, `readsUndeclared`. **Every entry carries a `salt`** (32 hex characters); with `UNSALTED_SEED`, the salt of entry `i` of a section is the first 16 bytes of `HMAC-SHA256(32 zero bytes, 'proof:' + section + ':' + i)` (D-14; `rules/0` is `4f6b739dbae8bd24e9b989ba83ac1ce8`).
  - `ProofRuleRef` gains a required `ruleSet` (`local` or a pack). Rules are cited by qualified id (`vat:R1`, D-37): two packs may each have a rule `R1@1`.
  - `outputs` (`ProofOutput`) is a list sorted by `name`, where it was an object keyed by name. Each carries its declaration in normal form (every member of `OutputDeclaration`: `values`, `rounding`, `unit`, `empty`, `per`, `dimension`, `sign`), a `status` (`OutputStatus`: `determined`, `provisional`, `conflict`, `undetermined`), `value?` (absent when there is none: `null` is a value, no longer "no value"), `bounds?` (`{ min?, max? }`, an undetermined ordered output only), `selected?` (`{ ruleId, subject? }`, the step a `max`, `min` or `highestPriority` took its value from), `contributors` and `pending` (rule ids).
  - `items` (`ProofItem`): one per element of an output `per` element, `{ output, subject, status, value?, bounds?, selected?, contributors, pending }`. A per output carries no value, bounds, selection, contributors nor pending rules: its items do.
  - `applied` (`ProofStep`), `skipped` (`ProofSkip`) and `exceptions` (`ProofException`) gain `status` and `subject?`; a skip gains `output?`, `detail?` and `instances?` (a grouped skip: `instances` with no subject, for `INACTIVE_DATE`, `DIMENSION_MISMATCH`, `TAG_MISMATCH` or `NOT_REQUESTED` only); a step gains `matches?` (the dimension values matched, `values` and `via`); an exception names what it affected (`affected`: `{ ruleId, subject? }`).
  - `pending` (`ProofPending`): the rules that could not be decided, `{ ruleId, version, subject?, output?, reason, detail?, missing, stratum }`, `missing` the pointers it lacked.
  - `factsRead` (`ProofFactRead`: `{ path, method?, status?, assertionDigest? }`, the assertion members together or none), `missingFacts` (`ProofMissingFact`: `{ path }`), `readsUndeclared` (`ProofUndeclaredRead`: `{ ruleId, version }`).
- **One order, so one digest.** Every list is sorted and has no duplicate, and `sealProof`, `signProof` and `verifyProof` refuse it otherwise (`<section> not sorted at i`, `duplicate output: name`, `rule decided twice: id@version at subject`, …): `rules` by (rule set, id, version), `outputs` by name, `items` by (output, subject), `applied`, `skipped` and `pending` by (rule set, id, version, subject; none first), `exceptions` in the order their carriers were processed (stratum, then rule-set precedence, priority descending, identity, subject; round 4 and 5, below), `factsRead` and `missingFacts` by pointer (`comparePointers`), `readsUndeclared` by rule, and the inner lists (`requested`, `strata[i]`, `imports`, `components`, `missing`, `matches` values and `via`, `affected`). Before, the producer was asked to sort `rules`, `applied` and `skipped`, and nothing checked it. A proof stored entry by entry and reloaded in any order gives the same digest once sorted (tested on 200,000 entries).
- **Each value has the form its declaration gives** (behaviour change): the output value, its bounds, those of its items, every contribution and `unrounded` value are checked against the whole declaration (`values`, `sign`, `dimension`, a count's integer, the type), and a rounded value against its step (`output value does not match its declaration`, `output value not rounded as declared`, `contribution does not match its output declaration`, `contribution not rounded as declared`). An `unrounded` value is allowed only with `rounding.at: 'contribution'`, and must round to its contribution (`unrounded value without rounding at contribution`, `unrounded value does not round to its contribution`).
- **Each value follows from its contributions** (new): `verifyProof` recomputes the combination of the applied contributions and refuses a value that does not follow (`output value does not follow from its contributions: name`): a `sum` exactly in decimal; a `number` sum in decimal to 20 significant digits, each partial sum rounded half away from zero, exactly as `@run-iq/core` sums (`core/src/engine/decimalArithmetic.ts`: `Float`, decimal.js `precision: 20` with `rounding: ROUND_HALF_UP` from `SETTINGS`, and `floatSum`, at core `adc85df`), then rounded at output: `0.1 + 0.2` is `0.3` and `0.30000000000000004` is refused, and `1e20 + 5 - 1e20` is `10` (the 21st digit of `100000000000000000005` is a tie, rounded away from zero; a half-even rounding would give `0`); a `count` of `true` contributions; `all`, `any`; a `union` keeping the first of equal items; the first greatest or least for `max` and `min`; the agreeing value of `highestPriority`'s contributors; the value a `shortCircuit` imposed; the empty value (`emptyOutput`) when no rule contributed. **The contribution order is normative: that of `contributors`, then that of `applied` for the steps of a rule not named.** It decides a `number` sum (`1e20, 5, -1e20` gives `10`; reordered `1e20, -1e20, 5` it gives `5`), the order of a `union`, and which of equal extremes a `max` or `min` selects. Since round 4 it is checked, whatever the strategy (below). The contributors must be the rules of the steps (`contributors differ from applied steps`), a selecting output names the step it took (`selected missing`, `selected does not match the value`), and an `all` no rule reached without `empty` is undetermined. All seven rounding modes are recomputed exactly, for a scale or an increment, linearly in the digits.
- **Statuses** (new): an undetermined output has no value; a per output's status is the strongest of its items' (determined without item); no output or item is weaker than a contribution feeding it, nor than an exclusion that would have fed it (`output status weaker than its contributions`, `… than its candidates`); a rule with undeclared reads is never determined. A step or pending rule of a per output goes to the deepest item containing its subject (`step feeds no item` otherwise), and an item's `pending` are the rules of the `pending` section that feed it.
- **Completeness, exceptions and decisions (round 2, new).**
  - A pending rule makes the output or item it feeds `undetermined` (D-7, the completeness table of Task 9M2), except an `any` with a `true` contribution, an `all` with a `false` one, and a `highestPriority` whose winner (the rule of `selected`) has a priority strictly above every pending rule that feeds it: `settled output with pending rules: name`. The priorities are the ones the proof records (round 3, below): `sealProof`, `signProof` and `verifyProof` decide it from the proof alone; a priority not recorded never outranks.
  - **Each listed rule records its priority** (round 3, new; `ProofRuleRef.priority`, required, a finite number, as its definition gives it). It enters the digest. Given `rules`, `verifyProof` refuses a recorded priority that is not the definition's (`rule priority mismatch: id@version`, after a matching checksum; `-0` and `0` are the same priority, as the canonical form writes them). - **Orders, tops, ranks and exception effects (round 4, behaviour changes).** One decision, one proof (D-16): every proof that only reorders an honest one is refused.
  - **Contribution order (D-5, D-23).** `contributors` and `pending` (of an output or item) are in contribution order: the precedence of the rule set (its place in `ruleSets`, a local rule without entry last), then priority descending, then identity (rule set, id, version, D-37). Refused otherwise: `contributors not in contribution order: name`, `pending not in contribution order: name`, for every strategy, commutative ones included (`[1e20, 5, -1e20]` or a decimal sum reordered no longer seals). `exceptions` are in the order their carriers were processed: stratum by stratum (round 5), then precedence, priority descending, identity, subject (none first); the exceptions of one carrier instance keep the order of its definition (`exceptions not sorted at i`). Before, `exceptions` were sorted by (rule, subject) only.
  - **`highestPriority` (I1).** Its contributors are exactly the applied rules at the top precedence and priority (D-23: precedence before priority); a rule below stays applied without contributing (`contributors differ from applied steps`; a forged lower contributor is refused). Top rules that disagree are a conflict: the winner is the first of them, each other is excluded `RULE_CONFLICT` with status `conflict` (`tie loser not in conflict: id@version`), and the output is `conflict` through its candidates (`@run-iq/core` `OutputCombiner`). Two top rules applied with different values give `output value does not follow from its contributions`.   - **Exception effects (I3, I6; format addition).** An exception gains `output?`: required for a `shortCircuit` (the output it targets), refused on any other kind (`exceptions[i].output is required for a shortCircuit`, `… applies only to a shortCircuit`), in the validator and the schema. Each kind is checked against the decisions it produced, and only those: an inhibition its `INHIBITED` exclusions, a short circuit the `SHORT_CIRCUITED` exclusions from its output, a substitution every later decision of the rules it affected (round 5, below). An affected entry `{ ruleId, subject? }` reaches the instances at its subject or under it, every instance without subject. Refused: an applied step an inhibition reaches (`inhibited rule applied: id@version`), an affected entry under which nothing was produced (`affected rule not inhibited|substituted|short-circuited by id@version: rule[ at subject]`), an `INHIBITED` or `SHORT_CIRCUITED` exclusion no such exception reaches (`inhibited without an exception`, `short-circuited without an exception`), a short circuit whose carrier has no step on its output while it affected rules or no other carrier won that output (`short circuit without its carrier applied`), and another step beside the carrier's on a short-circuited output (`steps beside a short circuit: name`). Only the carrier step on the short-circuited output is imposed (before, every step of the carrier was). The status check of D-7 (`decision weaker than the exception that affected it`) now applies only to the decisions an exception produced: a version `R@1` excluded `INACTIVE_DATE` beside an `R@2` inhibited by a provisional carrier is accepted (a false refusal before).
  - **Status equality (M1, D-7).** A settled output or item is the strongest of its causes, never stronger: its steps, its candidate exclusions (a tie loser's `conflict` among them), `determined` without any (`output status stronger than its causes: name`), or a tie among exceptions the proof shows (round 5, below).
  - **One output per rule (M2, D-21).** The steps, exclusions and pending entries of a rule name one output (`rule feeds two outputs: id@version`); a carrier's step imposed on a short-circuited output is the exception's effect and exempt. An exclusion without subject, not grouped, from a rule onto a per output feeds no item (`exclusion feeds no item: id@version`).
  - **Large lists (I5).** No list is spread into the arguments of a call any more (a `RangeError` on a few hundred thousand entries, reported as "too deeply nested"); problems stop at the issue cap. Tested in `tests/heavy/proof-size.test.ts`: 300,000 unsorted `factsRead` (`sealProof` refuses with `factsRead not sorted at 1`, `verifyProof` lists 100 problems and the limit), 200,000 affected rules and 250,000 contributors seal and verify, with linear work counted on property reads.
  - **`verifyProof` options (M5).** An option that cannot be read (a throwing getter, a Proxy trap) is an options problem: `options could not be read: <reason>`, `options.trustedKeys could not be read: <reason>`, `options.rules could not be read: <reason>`, no longer `proof could not be read`.

- **Substitutions, exception order and ties among exceptions (round 5, behaviour changes).**
  - **A substitution produced every later decision of the rules it affected:** a step, a pending entry (`UNDETERMINED`, or `ERROR` with `INVALID_PARAMS: …` when the model refuses the substituted parameters, D-8), an exclusion decided after the exceptions (`DOMINATED`, `RULE_CONFLICT`, any reason not decided before them, D-22). Not an exclusion decided before them (round 6: the reasons of core's filter, `RuleFilter`: `INACTIVE_DATE`, `TAG_MISMATCH`, `DIMENSION_MISMATCH`, `CONDITION_FALSE`, `DSL_NOT_FOUND`, `CONDITION_TIMEOUT`, `DSL_ERROR`; and `NOT_REQUESTED`), nor one another kind produced. The status check (`decision weaker than the exception that affected it`) holds for each of them; a pending entry is undetermined, never weaker. Before, a substituted rule that ended pending or dominated was refused (`affected rule not substituted by …`).
  - **Exclusion reasons are open (D-6; round 6).** The seven reasons D-8 took from core (`DSL_ERROR`, `CONDITION_TIMEOUT`, `DSL_NOT_FOUND`, `INVALID_PARAMS`, `CHECKSUM_MISMATCH`, `INVALID_RULE`, `OUTPUT_MISMATCH`) stay for plugins, and any unknown reason is accepted: such an exclusion is decided by the rule's own evaluation, after the exceptions, and means nothing more (those core's filter decides, above, come before the exceptions). Core's own invalid parameters stay pending `ERROR` (`INVALID_PARAMS: …`). Round 5 refused them; that refusal is withdrawn.
  - **`exceptions` order: stratum first.** Carriers are processed stratum by stratum, so an exception of stratum 0 comes before one of stratum 1 whatever their priorities; then precedence, priority descending, identity, subject.

- **Messages that changed.** A value of the format that must be a list says `<path> must be a list`. An empty string is refused wherever a text is expected (a skip's `detail`, a `sourceRef`); a text with a lone UTF-16 surrogate is refused everywhere (`<path> contains a lone UTF-16 surrogate`). `evaluatedAt` is `null`, a civil date or a canonical instant that exists, `sealedAt` a canonical instant. An output name starting with `$` is now refused by `validateProof` (a shape error at `outputs[i].name`) rather than by the consistency checks (`output name reserved` is gone). `strata` errors and the duplicate rule check cite qualified ids. `unrounded` is reported only when it is present without a contribution rounding, or does not round to its contribution.
- **Validator, schema and normal form agree.** `schema/decision-proof.schema.json` is regenerated for the new format: it carries the output declaration rules and the normal form (`empty: false`, `rounding.at: 'output'` and an increment that is a scale are refused), and agrees with `validateProof` on every shared case, on the special characters of each pattern (subjects, pointers, names, pack ids, time zones, salts, codes, `declaredBy`, matched dimensions) and on 10,000 drawn declarations inside a proof. What the schema cannot check is listed in its description: the uniqueness of qualified rules, lone surrogates, the dates of a time segment, the depth and count of values.
- **Linear.** Every consistency check is linear in the size of the proof (counted on property reads and digits); a proof of 80,000 steps verifies with property reads linear in their number (`tests/heavy/proof-size.test.ts`, counted at 40,000 and 80,000 steps; round 4 replaced a wall-clock bound).

## The proof tree and redaction (Task 9K1)

**Behaviour change: the proof digest and `sealProof` change.** A proof sealed before has another digest: seal it again from its decision.

- **The digest is a tree (D-16): its exact encoding, and its vector.** With `T = utf8(proof.format) ‖ 0x00` (`run-iq.proof/1` today), the format of the proof itself, for every leaf and for the digest:
  - leaf 0, the header: `sha256(0x00 ‖ T ‖ utf8(canonicalize({ s: 'header', e: H })))`, `H` the proof without `digest`, `signature` and the ten sections of `PROOF_SECTIONS`, holding `counts`; the header is never redacted;
  - then, section by section in the order `rules, outputs, items, applied, skipped, pending, exceptions, factsRead, missingFacts, readsUndeclared`, one leaf per entry: `sha256(0x00 ‖ T ‖ utf8(canonicalize({ s: section, i: index, e: entry })))`, `index` the place (from 0) of the entry in its section, its `salt` inside `entry`; an empty section gives no leaf; a redacted entry `{ redacted: h }` gives the 32 bytes of `h` as they are;
  - node `sha256(0x01 ‖ left ‖ right)`, RFC 6962 split, empty tree `sha256('')`;
  - `digest = sha256(0x02 ‖ T ‖ uint64be(n) ‖ root)`: it commits to the number of leaves, as the input digest does, and swapping two entries changes it (the index is in the leaf). The signature covers the 64 characters of `digest`.
  - `proofLeafHashes(p)` gives every leaf, `proofLeafHash(leaf, format)` one leaf, both through the same internal encoder (`hashLeafInto`); `sealProof`, `verifyProof` and `redactProof` use them (`verifyProofInclusion` takes a leaf hash and uses neither).
  - `tests/vectors/proof-v1.json`, recomputed by an independent Python script (stdlib only): the plan's proof sealed under the seed of `input-v1` (`f9b972f5…aacfb`) has 4 leaves, header leaf `8afb81c07ea4067c15d2020df6b6d23871a92f25411bba48bc0e08c805f650aa`, root `edfbff2c7179435bf978db2871f0137b7fdb2476804c0e63b267abc0648d80fe` and digest `acfaa494f781e65df2c0b70a29d440f462427f4e46cc91c66b23a45e0e88f2e3`; the richer redacted proof has 21 leaves and digest `7bfdaf5aa05e46565ab3573eb62d2dd599ceecc9a515463d49e84049fe25f600`.
- **What the header shows, and why (D-16).** The header is one leaf, never redacted, so everyone who sees the proof sees it. Each member is justified as not depending on the input: `format`; `inputDigest` and `inputSalted`; `sealedAt`; `timeZone`; `ruleSets` (identities and digests of public packs and referentials); `versions` (software: a component never carries an input value, the contract of D-25); `strata` and `requested` (output names taken from the rules received and the options alone, never from the input); `supersedes` (a digest and a code); `counts` (the number of entries of each section); `requestId`, which the README asks to keep opaque; `evaluatedAt`, the reference date of the decision. `evaluatedAt` is shown by choice: without it a verifier cannot tell which versions of the rules had to apply. A personal date a rule reads through `effectiveOn` is a named date of `meta.dates`, so a leaf of the input tree, never a header member. Everything that depends on the input sits in a section entry, redactable: outputs (value, status, contributors; the name stays visible in `strata` and `requested`), items by subject, steps, exclusions, pending rules, exceptions, facts read, missing facts and undeclared reads.
- **Redaction and disclosure are reserved to salted proofs and inputs (D-14).** Under `UNSALTED_SEED` the salts are public HMACs, so a hidden entry or a hidden neighbour leaf could be found again by hashing candidates. `redactProof` throws `INVALID_DISCLOSURE` (`unsalted proof cannot be redacted`) and `discloseFacts` throws `INVALID_DISCLOSURE` (`unsalted input cannot be disclosed`), the seed compared by its bytes. A redacted entry found in an unsalted proof (made by hand) keeps it at best `consistent-redacted`. Erasing the secret of a person (`deriveInputSeed` with a per-person secret) cuts the link: under another seed nothing verifies.
- **Every leaf under the proof's own format (Task 9K2, round 1, API change).** `proofLeafHash` and `verifyProofInclusion` take the format to hash under, the proof's `format`, as their last argument; nothing hashes under the constant `PROOF_FORMAT`. Before, both hashed an entry and the digest under `run-iq.proof/1` whatever the proof, which a following format would have broken. A test lists a second, synthetic format and checks both functions, the header and the digest under it against `node:crypto` (`tests/proof-format-tag.test.ts`).
- **The header counts the entries of each section (`counts`, new, review of 9K1).** `sealProof` adds `counts`, the number of entries of each of the ten sections (`ProofCounts`), to the header, so the digest commits to them. Without it, a redacted entry moved from the end of a section to the start of the next, empty, kept every leaf in its place and the digest with them. `validateProof` alone refuses a section whose length, redacted entries counted, is not its count (`counts.<section> is <m>, <section> has <n> entries`); the schema requires `counts`, each a safe integer from 0. `UnsaltedProof` has none (sealing adds it).
- **`sealProof(content, seed?)` salts the entries.** A content past `MAX_JSON_VALUES` by itself is refused naming the value that passes it (`Cannot seal the proof: <path> is too large: …`); one that fits but whose salts would not, with `Cannot seal the proof: the salts of its <n> entries would take it past 10000000 values`. It takes the content without salts (`UnsaltedProof`, `Unsalted<T>`; an entry with a `salt` or redacted is refused) and sets each salt to the first 16 bytes of `HMAC-SHA256(seed, 'proof:' + section + ':' + index)`, in hex (D-14). `seed` defaults to `UNSALTED_SEED`; under a secret seed (the one of the input digest, `deriveInputSeed`), the salts hide the entries. `inputSalted` must match the seed (`Cannot seal the proof: inputSalted does not match the seed`): `true` with a secret seed, `false` with `UNSALTED_SEED`. A seed that is not 32 bytes is refused first (`INVALID_KEY`).
- **`redactProof(proof, hide)` (new)** replaces each entry `hide(section, index)` picks with `{ redacted: <hex of its leaf> }` (`Redacted`). The leaves, the digest and the signature are unchanged. The header is never redacted. It reads `proof` once, checks it and its digest before calling `hide`, calls `hide` once per entry not already redacted, in the order of the leaves, and refuses: `INVALID_PROOF` (`Cannot redact the proof: …`) a malformed proof or one whose digest does not match; `INVALID_DISCLOSURE` an unsalted proof (`unsalted proof cannot be redacted`: its salts are public, a hidden entry could be found again by trying candidates), a `hide` that is not a function, that throws (`hide failed for <section>[<i>]: <reason>`) or that returns something else than a boolean (`hide must return a boolean, got <type> for <section>[<i>]`).
- **Checking one entry alone (new).** `proofLeafHash(leaf, format)` hashes one leaf (`ProofLeaf`: `{ s: 'header', e }` or `{ s: section, i, e }`, checked as `validateProof` checks it; a redacted entry gives its hash as it is) under `format`, the proof's format: a format not in `PROOF_FORMATS` throws `INVALID_PROOF` (`invalid proof leaf: unknown format: <format>`) before the leaf is read, and a header of another format `invalid proof leaf: the header is of format <f>, not <format>`. `verifyProofInclusion(digest, size, index, leafHash, path, format)` checks it against the signed digest with its audit path (`inclusionPath`): it reads the digest, the leaf and the ⌈log2 n⌉ hashes of the path, never the other leaves, and never throws (`false` for an unlisted format).
- **`verifyProof` on a redacted proof: never the full verdict (review of 9K1).** The digest is recomputed from the leaves (`digest mismatch` if a hash was altered). The preimage of a redacted entry is never checkable: its leaf hash is all the proof shows, and a producer can put any hash there (a fake marker the signature then binds). So a proof with a redacted entry proves its visible entries only: it is `authentic-redacted` where it would be `authentic`, `consistent-redacted` where it would be `consistent` (`ProofStatus`), never `authentic`, lifted check or not. `redacted: n`, the notice `redacted entries: n` and `lifted` (`LiftedCheck[]`) come with it, `lifted` also when it is `invalid`.
- **A check is lifted, and named.** A check that a redacted entry could satisfy is not failed while a section it reads has one: it is lifted. Each check finds its problem on the visible entries first and asks to be lifted only then, so `lifted` lists the checks a redaction actually kept from failing, each `{ check, redacted }` with the redacted sections that could explain what it found, in a fixed order, and a notice each: `check lifted: <check> (<sections> redacted)`, e.g. `check lifted: output value from its contributions (applied redacted)`. `lifted` is absent when no entry is redacted, `[]` when entries are redacted but no check was lifted. What the redacted entries can explain is counted for the whole proof (review of 9K1, rounds 4 and 5). Each problem lifted says, for each section whose hidden entry could change the computation behind it, what that entry would need to carry to explain it: a rule (`id@version`, or `id` when only the id is cited, with the subject of a carrier instance), an output (a rule feeds one, an exception and an exclusion are of one), an output and its item (a step feeding an item, an item of a collection), the rule and the output of one entry (a pending rule missing from an output), or nothing it can tell (`free`: one entry may explain any number of such problems, the reason given in `LIFTS`). A check computes from more than the entry it names: the ties among exceptions derive from the exclusions `RULE_CONFLICT`, the exceptions before and the standings of their carriers, so while a hidden `rules` (a short circuit in the proof), `skipped` or `exceptions` entry may change them (two exception records, visible or redacted, and an exclusion `RULE_CONFLICT` visible or `skipped` redacted: a tie needs a winner and a loser, or, R15, an exception fired before the one it discarded), every problem computed from them is free there: a carrier's missing step, a loser, a tie record, a status against its tie or its causes, the decisions of a fired carrier, the exceptions behind exclusions, the carrier records. Where the computation reads less, the problem asks less: a `sum` reads no standing, so no `rules` entry lifts its value; nothing hidden settles a `sum` with a pending rule. Two requirements one entry could meet together (equal wherever both give a field, in a section both allow: `Z` and `Z@1`, an output and an item of it) are counted once; others (`Z@1` and `Z@2`, two outputs, two items, two pairs) need distinct entries. The requirements are matched to the redacted entries of their sections by Hall's condition, rules, outputs and the pairs of `both` each: for every set of sections, the requirements allowed only there are no more than its redacted entries (at most 2^10 sets, linear in the problems). If it holds, the checks are lifted and named in `lifted`; if not, no check is lifted, every problem lifted is reported, and the proof is `invalid` (`lifted: []`). The guarantee: k redacted entries never excuse problems that need more than k distinct entries, counted this way; and a redaction of a proof `verifyProof` does not find `invalid` is never `invalid`, because each problem it raises may be explained in every section whose hidden entry could change its computation (the audit of each check is in `LIFTS` and the report of Task 9K1, round 5), and the count of distinct entries never exceeds the truth. The tests check it on every subset of the entries of five proofs (ties and exceptions among them) and on 64,063 redactions of the 364 proofs of the review's corpus (`tests/heavy/redact-corpus.test.ts`). A step, pending rule or exclusion of a per output that no item, visible or not, could feed (a grouped exclusion, a subject under no element of the collection) is reported whatever is redacted. The checks and the sections that may lift them (`src/proof/lifts.ts`; `tie`: while the ties may be hidden): cited rules listed (`rules`); cited outputs, requested outputs and stratum outputs listed (`outputs`); the output value from its contributions (`rules` for a `highestPriority`, `applied`, `exceptions`); an output status no stronger than its causes (`applied`, `skipped`; `rules`, `exceptions` by `tie`); an output status no weaker than its tie, a short circuit tie with its loser excluded, the tie records against their carriers (`rules`, `skipped`, `exceptions` by `tie`); an undetermined output with a cause, the pending rules of an output, the pending carrier chain (`pending`); a settled output without pending rules (`rules` for a `highestPriority`, `applied` for it, an `any` or an `all`); a rank within its instances (`applied`); a short circuit with its carrier applied (`applied`, `exceptions` when it affected nothing; `rules`, `skipped`, `exceptions` by `tie`); the items of a per collection and a per output against its items (`items`); the form of a count, the decisions against the exceptions, a pending carrier fired with its exceptions, an exception status as its carrier decided (`exceptions`); an exclusion with its exception and the decisions of a fired carrier (`exceptions`; `rules`, `skipped` by `tie`); every listed rule decided (`applied`, `skipped`, `pending`, `exceptions`); the rules an exception affected (those four; `rules` by `tie`); the carrier exception records against definitions (`skipped`, `exceptions`; `rules` by `tie`); a conflict status with its tie (`skipped`); a provisional status with its source (`factsRead`, `readsUndeclared`); the rules given against the proof (`rules`). A redaction of a section a check does not read lifts nothing: the check fires as without it. A citation of a rule or an output a redacted entry may hold is the lifted check `cited rules listed` or `cited outputs listed`, with no other notice. What the visible entries contradict is still refused (an output weaker than a visible contribution, an unsorted section). The places messages cite are those of the proof, redacted entries counted (`applied not sorted at 2`). The carries of Task 9J:
  - a `provisional` status needs no visible source while `factsRead` or `readsUndeclared` has a redacted entry, a `conflict` none while `skipped` has one; without such a redaction it is still refused;
  - a rule pending `PENDING_CARRIER` may have its carrier, or the root of the chain, in a redacted `pending` entry: `pending carrier without a pending carrier` and `without a root` are not reported while `pending` has a redacted entry. A redacted pending entry is plain `{ redacted }`: keeping its `fired`, reason or `carrier` visible would show the rules it names;
  - with `rules`, the rules given that the proof does not show are compared by number with its redacted rules: `rules check incomplete: n redacted rule(s)` keeps the proof at best `consistent-redacted`; `unexpected rules: u given, not in the proof (n redacted)` and `rules missing: m redacted, not given` make it `invalid`. The checks of a carrier's exception records against its definition are lifted while `skipped` or `exceptions` has a redacted entry, each needing a hidden record or exclusion of that carrier instance (any, while the ties may be hidden: who lost decides what a carrier records); each rule given and not shown needs a hidden rules entry of that `id@version`.
  - A redacted entry in an unsalted proof (made by hand) keeps it at best `consistent-redacted` (`redacted entries in an unsalted proof`).
- **`signProof`** signs a redacted proof as `verifyProof` checks it: the digest is that of the proof it was redacted from.
- **Shape.** `validateProof` and the schema accept `{ redacted }` (64 lowercase hex characters, nothing else) in place of any entry of the ten sections; `validateProof` alone refuses the same leaf hash twice (`<section>[i] repeats the redacted leaf of <section>[j]`). New types: `Redacted`, `ProofHeader`, `ProofCounts`, `LiftedCheck`, `Unsalted<T>`, `UnsaltedProof`, `ProofLeaf`; the sections of `UnsignedProof` and `DecisionProof` are lists of entries or `Redacted`; `ProofVerification` gains `redacted?` and `lifted?`; `ProofStatus` gains `authentic-redacted` and `consistent-redacted`.
- **Frozen vector.** `tests/vectors/proof-v1.json`, recomputed by an independent Python script (stdlib only): the plan's proof sealed under the seed of `input-v1`, its salts, leaves, root and digest, and a richer proof (escapes `~0` and `~1`, astral characters, non-integer numbers, nested lists, twelve rules, a redacted entry). The plan's header leaf, rule leaf and digest are kept in it with the reason they differ: an input digest before Task 9H2 round 3, a rule without the priority Task 9J made required, a digest without the leaf count. Refrozen in the review of 9K1 when the header gained `counts` (only the header leaf, the root and the digest change); the values of the first round are kept in it (`round1`) and rebuilt by the tests.
- **Cost, counted.** `sealProof` makes one sha256 per leaf, one per internal node, one for the digest and one HMAC per entry (its salt); `verifyProof` the same without the salts: counted exactly at 80,000 and 250,000 steps, with the bytes hashed linear in the steps (`tests/heavy/proof-scale.test.ts`, which also counts the reads of one leaf checked among 200,002). A short entry is written as one text and hashed at once, a longer one streamed. The hash stays the pure JavaScript sha256 of `@noble/hashes`, so a browser verifies as Node does.
- **Measured, not asserted** (Task 9K1, built `dist`, Node 24, one machine; the budgets are the D-26 bench's): seal then verify of a sum of 80,000 steps took 2.3 to 2.5 s before this task (one sha256 of the canonical proof, salts given by the caller) and 2.8 to 3.6 s after; of 250,000 steps, 7.4 to 8.4 s before and 9.8 to 10.4 s after. The plan's targets were 3 s and 8 s.

## Detached attestations and the format policy (Task 9K2)

- **An attestation is a signed statement kept apart from the proof (D-29).** `Attestation` (`run-iq.attestation/1`, `ATTESTATION_FORMAT`) is `{ format, kind, subject, keyId, role?, claims?, at, signature }`: `kind` an open non-empty string; `subject` (`AttestationSubject`) exactly one of `{ proofDigest }` and `{ keyId }`; `keyId` and `role` non-empty strings; `at` a canonical instant; `signature` an ed25519 signature in unpadded base64url (86 characters). The envelope is closed whatever the kind: any member but these is refused (`attestation has an unknown key "<key>"`).
- **`claims`, the one member reserved for later kinds (ruling 9K2-8, round 1).** D-29 promises that a later kind (`timestamp`, `revocation`) is a new value of `kind` in the same format, never a new format. What such a kind needs beyond the envelope (a timestamp token, a revocation reason) goes in `claims`: a plain JSON object, read once and checked as input values are (no lone surrogate, numbers of absolute value below 2^53, at most 1000 levels, every value counted in the 10,000,000-value budget), covered by the signature like every other member, and never interpreted by this version. A `cosignature` takes none: `claims` on one is `invalid` (`cosignature takes no claims`, its content not read). On a kind this version does not verify, `claims` are checked for their shape and signed, and the verdict stays at best `consistent` with `attestation kind not supported: <kind>`. An attestation without `claims` signs the same bytes as before: `createAttestation` writes none, and the frozen vector is unchanged (tested). Problems are named at their path: `/claims must be a plain JSON object`, `/claims/n is not JSON: NaN`, `number beyond 2^53 at /claims/n`, `/claims/list is too large: more than 10000000 values`, `/claims could not be read: <reason>`. A proof keeps its one `signature`: a reviewer, an auditor or a timestamping service adds an attestation beside it, never inside it.
- **The signature covers `canonicalize` of the attestation without `signature`** (JCS), its UTF-8 bytes signed with ed25519 (strict RFC 8032). That message is a JSON object holding `format`, never the 64 characters of a proof digest, so a proof signature cannot pass for an attestation and an attestation signature cannot pass for a proof's (tested both ways).
- **`createAttestation(proofDigest, privateKey, keyId, { role?, at? })`** returns a cosignature: `kind: 'cosignature'`, `subject: { proofDigest }`, `at` defaulting to the current time (the caller's clock, read only when `at` is absent). It refuses, in this order: a digest that is not 64 lowercase hex characters (`INVALID_ATTESTATION`, `proofDigest must be 64 lowercase hex characters`); a `keyId` that is empty, not a string or holds a lone surrogate (`INVALID_KEY`); options that are not `undefined` or a plain object `{ role?, at? }`, or whose members are not valid (`INVALID_ATTESTATION`, `Cannot attest: <problem>`, read once like any other input); a private key that is not 64 hex characters (`INVALID_KEY`); an attestation whose canonical text no JavaScript string can hold (`INVALID_ATTESTATION`, `Cannot attest: … too long to write as one string`).
- **`verifyAttestation(a, proofDigest, trustedKeys)` never throws.** It returns `{ status, issues }`:
  - `invalid` for a digest argument that is not 64 lowercase hex characters (`the expected proof digest must be 64 lowercase hex characters`), a malformed attestation (each problem named by its path: `/at must be an instant in its canonical form YYYY-MM-DDTHH:MM:SS.sssZ`, `/subject must hold exactly one of proofDigest and keyId`, `/kind must be a non-empty string`, `/subject could not be read: <reason>`), an unknown format (the single issue `unknown format: <format>`), a cosignature over a key (`cosignature needs subject.proofDigest`), another proof (`attestation for another proof`, whatever the kind), `trustedKeys` that is not a plain object (`trustedKeys must be an object of hex public keys`) or cannot be read, an attestation too long to verify, and `signature invalid`. Task 9K5 adds three: a kind this version does not verify (`attestation kind not supported: <kind>`), a `{ keyId }` subject (`attestation not about this proof`) and a malformed trusted key (`trustedKeys.<keyId> is malformed`);
  - `consistent` for a valid signature under an unlisted key (`untrusted key`; only own keys of `trustedKeys` count, and `undefined` trusts none): a cosignature of the proof whose signer is not trusted. Before Task 9K5 a malformed trusted key and an unsupported kind were `consistent` too; both are `invalid` now (below);
  - `authentic` for a cosignature of `proofDigest` whose signature a trusted key verifies, with no issue.
- **What a verdict says about the proof.** Only `authentic` on a `cosignature` attests the proof whose digest is passed. Every other attestation is `invalid`, so no `timestamp` or `revocation` can be read as a weak yes for a proof (Task 9K5 revises D-29, which said "at best `consistent`").
- **Hostile input.** The attestation is read once into a plain copy, each property read and counted once (a throwing getter, a Proxy, a revoked Proxy, duplicate own keys, 10,000 levels of nesting, a 10,000,000-character role, a Proxy list claiming 2^32 − 1 elements: each a named `invalid`, never an exception). Its cost is linear in its size: the reads are counted by tests (`tests/attestation-hostile.test.ts`, and `tests/heavy/attestation.test.ts` for an object past `MAX_JSON_VALUES` and a role of 2^29 − 24 characters).
- **Schema.** `schema/attestation.schema.json` (exported) accepts the attestations `verifyAttestation` finds well formed, `claims` included (an object, refused on a `cosignature`); only the verifier checks lone surrogates, the numbers, depth and size of `claims`, the subject against the expected digest, and the signature.
- **Frozen vector `tests/vectors/attestation-v1.json`**, computed with `node:crypto` alone: the RFC 8032 test 1 key, `keyId` `reviewer-1`, `role` `human-review`, `at` `2026-11-01T10:00:00.000Z`, over the digest of `proof-v1` (`acfaa494…f2e3`), signature `8BY9WNtOY18OdFrkzkJQ9aDLgIAi_u0X_RXrjOCaaDeBx13tynAly6Ne45Kxx1nPa8-NL8JOsut7kMPzehxiBw`. Each built entry reproduces it.
- **Format policy, tested (`tests/formats.test.ts`).** `PROOF_FORMATS` is frozen and lists the proof formats only (the annex constants are checked apart); every listed format seals and verifies (`consistent`, then `authentic` once signed); the domain tag is recomputed with `node:crypto` from the proof's own `format` (every leaf, the RFC 6962 root by an independent recursive implementation, the digest); an unknown format gives a single issue for proofs, `validateProof`, `sealProof`, disclosures and attestations.
- Both entries export `ATTESTATION_FORMAT`, `Attestation`, `AttestationSubject`, `createAttestation` and `verifyAttestation`.

## Verification and rules fail closed (Task 9K5)

Owner decision of 2 November 2026, after the fail-closed audit: the engine never guesses, nothing passes silently, and a verifier says what it did not check. Every item below is a change of behaviour.

- **`verifyProof` says what it did not check (I10).** A verdict that is not `invalid` carries notices in `issues`, after the others:
  - without `rules`: `rules not checked: pass rules to compare checksums, priorities and carriers`;
  - always: `conditions and amounts not checked: verifyProof does not replay the decision`. `verifyProof` executes nothing, so conditions and amounts are checked by replay only (Task 11, core). An `invalid` verdict stops at its problem and carries neither notice.
  - The README says what each call checks. `authentic` still needs a matching digest and a signature by a trusted key; with the notices it no longer reads as "checked against the rules" when it was not.
- **With `rules`, `verifyProof` checks what the definitions decide without execution (I11).** Only rules whose checksum matched. Each contradiction makes the proof `invalid` and is named by the rule instance (`r1@1`, `r1@1 at /items/@a`):
  - `rule applied outside its window: <rule>`: the window `[effectiveFrom, effectiveUntil)` of an applied step does not hold `evaluatedAt`;
  - `rule skipped as INACTIVE_DATE but its window contains evaluatedAt: <rule>`;
  - `applied model differs from its rule: <rule>`;
  - `applied output differs from its rule: <rule>`, and `skipped output differs from its rule: <rule>` for the exclusions made before the exceptions (an `output` is the rule's own, or the target of one of its short circuits, qualified by the rule set);
  - `CONDITION_FALSE on a rule without a condition: <rule>`;
  - `DIMENSION_MISMATCH on a rule without dimensions: <rule>`.

  `evaluatedAt` is `meta.dates.effective`, the reference date of a rule without `effectiveOn`: the window is compared only for such a rule, in the time zone of the rule, then of its rule set, then of the decision. A pending entry is checked like an applied one (`rule pending outside its window: <rule>`), and `NOT_REQUESTED` against the header's `requested`. Time zones: `UTC` and `±HH:MM` are exact. For an IANA name each bound of a civil window is decided on its own, knowing only that the offset of a zone stays within -24:00 and +24:00 (Sitka before 1867 is +14:58): an instant a day or more from a bound is on the same side of it in every zone. Inside that band the offset of the zone at that instant is read from the runtime (`Intl`, local mean times included) and the window is decided; only a zone the runtime does not know leaves it undecided (`zone <zone> unknown to this verifier`). A day that holds an instant bound of the window is undecidable in any zone (`the day holds the bound of the window`). `options.calendar` (a `CivilCalendar`) decides when given. Other undecidable windows: `(effectiveOn is <pointer>)`, `(no evaluatedAt)`, `(the day holds the bound of the window)`; rules with one kind of cause share one notice (`window not checked for 150 rules (<kind>): r000@1, … and 145 more`), so the number of notices of a verdict is fixed. An unexpected failure of a check is `invalid` (`window check failed: <message> (<rule>)`). A reason this check does not decide, unknown ones included (reasons are open, D-6), gets the notice `reason not checked: <reason>`, once per reason (twenty, then a count); `INHIBITED`, `SHORT_CIRCUITED` and `RULE_CONFLICT` are verified against the exceptions and get none. Redacted `applied`, `skipped` and `pending` entries are counted in a notice (`1 applied entry redacted: not checked against rules`). The notices are few and fixed in number (one per kind of cause, twenty reasons then a count), so a verdict that is not `invalid` never reaches the 100-message bound; when an `invalid` verdict does, the redaction notices are kept, the other findings give way, and a last notice says how many were left out (only when some were). `verifyProof` refuses an option key it does not know (`options.calender is not an option (did you mean calendar?)`). A `NOT_REQUESTED` exclusion without its `output` is `invalid`.

- **An attestation of a kind this version does not verify is `invalid` (I12, D-29 revised).** `attestation kind not supported: <kind>` is no longer a warning under `consistent`: a `revocation` of the signer's key, a `timestamp` or a `cosignature-v2` cannot be read as a weak yes for a proof. A `{ keyId }` subject verified against a proof digest is `invalid` too: `attestation not about this proof`. The envelope and the signature are still checked, so every problem is listed. The schema `attestation.schema.json` still accepts these attestations (they are well formed); its description says that the verifier refuses them.
- **A malformed trusted key is `invalid` (M1).** `trustedKeys.<keyId> is malformed`, in `verifyProof` and in `verifyAttestation`, for any key of `trustedKeys`, whoever signed: a broken trust anchor is a configuration error of the caller, never ignored. The cost is linear in the map, which the caller controls.
- **An unknown top-level field of a rule is refused (I13).** Every own key is read, enumerable or not, string or symbol (`unknown rule field: Symbol(tag)`). `unknown rule field: <key>`, with `(did you mean <field>?)` when the key matches a reserved field without case or one edit away (a letter more, less, changed or swapped): `dominancegroup`, `effectiveUntill`, `exception`. It is refused whatever its value, `undefined` included, by `validateRuleDefinition` (the issue path is the key), by `normalizeRuleDefinition` and so by every function that reads a rule. Extensions go under `extensions`, a plain object: a name there is free, a reserved one included, and its values are free-form JSON, except that a name whose value is `null` is refused (below the first level, `null` is data). `extensions` enters the checksum and the fingerprint; an empty one is dropped, as absent. `RESERVED_RULE_FIELDS` lists `extensions`; `RuleDefinition` and `RuleDefinitionInput` have no index signature any more, and `ExecutableRule` has `extensions`.
  - **Checksums.** The checksum of a rule with no extension is unchanged: the frozen checksums are tested (`tests/rule-fail-closed.test.ts`), and so are the frozen proof vectors. A rule that had top-level extension fields changes its checksum and its fingerprint, because its fields move under `extensions`; a stored record of such a rule is refused by `fromStoredRecord` until it is written again. Consumers: `@run-iq/core` for rules with extensions, `plugin-fiscal`, and `rule-registry` and `dsl-jsonlogic` for any rule field outside the schema.
- **`null` is refused in a rule (M8).** `<field> is null: omit the field instead`, for every optional field (`condition`, `timeZone`, `effectiveOn`, `forEach`, `ruleSet`, `output`, `dimensions`, `tags`, `dominanceGroup`, `exceptions`, `sourceRef`, `extensions`), and `dimensions.<name> is null: omit the field instead` inside `dimensions`: a column that is lost must not widen a rule (`effectiveUntil: null` ended nothing, `dominanceGroup: null` joined no group). `effectiveUntil` and `checksum` are on the list: "no end" is written by omitting `effectiveUntil` (ruling of the machine session, 2 November). `undefined` and an absent field are the same input. There are two forms: what an author writes never holds `null`; the normalized form keeps `effectiveUntil: null` as its internal encoding of "no end", and the functions that read it back accept that one `null`. **Which function reads which form is written once, in the README ("Rule definition").** `checksum: null` is refused in both forms: a stored rule always has its checksum. `validateStoredRuleDefinition` is the validator of the stored form (it accepts `effectiveUntil: null` and nothing else the authored one refuses): `hydrateRule` of core lists the problems of a row with it. No checksum changes: the frozen checksums are tested in both forms. A `null` below the top level is data, as before (`params`, `condition.value`, `exceptions`, and below the first level of `extensions`); a name of `extensions` whose value is `null` is refused (`extensions.<name> is null: omit the field instead`): a plugin that has no value omits the name. `findOverlappingVersions` refuses a `null` `ruleSet`, `effectiveOn` or `timeZone`, and `windowContains` and `isEffectiveAt`, which read the window and its `timeZone` only, refuse a `null` `timeZone` (audit finding 6). `checksum` must be a string when present (`checksum must be a string`). The JSON schema agrees: `additionalProperties: false`, `extensions`, no `null` anywhere at the top level.
- **A date holds at most three fractional digits (M9).** Every live grammar already refused it (rule bounds, `evaluatedAt`, `sealedAt`, the date of an attestation, the named dates of an input) and a test now pins that on each path. `parseRuleDate`, the only grammar that truncated, had no caller and was not exported: it is removed.
- **Tests.** `tests/proof-verify-closed.test.ts`, `tests/rule-fail-closed.test.ts` and the updated attestation tests. The notices are filtered by `tests/notices.ts` where a test looks at the problems only.
